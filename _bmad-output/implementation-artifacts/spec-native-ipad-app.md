## Intent

**Problem:** Chronicle currently runs as a React web product and Electron Mac package, so it cannot be signed, installed, or exercised as an application on Chris's connected iPad Pro running iPadOS 27. Its existing assistant also calls a server API that may route to paid external LLMs, which violates the Apple-only inference requirement.

**Approach:** Add a signed SwiftUI iPad target that packages the existing Chronicle interface and local content inside the app, hosts that content over an app-owned loopback service for reliable browser routing, and provides a native Apple Foundation Models companion with no external LLM fallback. Build with Xcode 27 beta, install on the attached M2 iPad, launch it, and verify the live device result.

## Boundaries & Constraints

**Always:** Use Xcode 27 beta and the iPadOS 27 SDK; target the connected M2 iPad; preserve the current Chronicle rooms and iPad-responsive behavior; keep user state on-device through the existing persisted browser store for this first installed slice; serve only bundled assets over `127.0.0.1`; check `SystemLanguageModel` availability at runtime; use Apple Foundation Models for native generation; expose honest unavailable/error states; keep touch targets and safe-area behavior appropriate for iPad.

**Ask First:** Changing the existing web product's feature behavior; adding CloudKit schema or production entitlements; replacing the React surfaces with a broad native rewrite; changing the app's commercial deployment floor; deleting or migrating existing Chronicle data.

**Never:** Call OpenAI, Anthropic, Google, or another external model; add third-party LLM SDKs or keys; depend on the Mac-hosted Chronicle server for launch; claim server-only import, OCR, voice, or database routes work on-device when they are not implemented; commit generated web bundles, DerivedData, credentials, device identifiers, or provisioning profiles.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|---------------|----------------------------|----------------|
| Installed launch | App launched on connected iPad | Bundled Chronicle interface opens without a Mac server and all main rooms remain navigable | Show a native recovery state if the loopback host or bundle cannot start |
| Apple model available | User opens native companion and submits a prompt | Response is generated by `SystemLanguageModel` and displayed in the app | Surface generation errors without external fallback |
| Apple model unavailable | Intelligence disabled, downloading, or otherwise unavailable | Chronicle remains usable and explains the exact availability state | Disable submission until the model becomes available |
| Unsupported server feature | Web surface calls a route not present in the iPad host | Existing local state remains intact and the UI receives a truthful local error | Never redirect the request to a remote Chronicle host |

## Design Notes

This is the narrowest honest path to a useful installed application: preserve the mature Chronicle UI while placing lifecycle and intelligence under native Apple control. The loopback host exists only inside the process and serves bundled files; it is not a backend dependency. Server-heavy features remain visibly unavailable until their storage/import implementations are migrated to Apple frameworks.
