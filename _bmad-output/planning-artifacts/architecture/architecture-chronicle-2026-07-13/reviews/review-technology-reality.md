# Technology Reality Review — Chronicle CloudKit Sync and Handoff

**Verdict: NOT IMPLEMENTATION-READY.** The core CloudKit direction is viable on the local Xcode 27 beta: a private database, custom record zone, `CKSyncEngine`, change-tag conflict detection, `CKRecord.encryptedValues`, encrypted `CKAsset` fields, same-zone references, and atomic zone batches all exist. However, the handoff currently overstates what the checked-in app implements, leaves atomicity and record-size behavior unsafe, and does not yet contain the entitlements or multi-device targets needed to exercise the claimed system. Treat the documents as a sound design direction that requires the critical/high corrections below before implementation work is split across developers.

## Evidence basis

- Local beta toolchain: `/Users/chris/Downloads/Xcode-beta.app`, Xcode `27.0` build `27A5218g`, iOS SDK `27.0` build `24A5380g`, Swift compiler `6.4`; the project explicitly selects Swift language mode `6.0` and iOS deployment target `27.0` in `apple/project.yml:4-16`.
- The generated native target and `CloudKitSyncModel.swift` compile under the Xcode 27/iOS 27 SDK. A simulator test build completed compilation and linking; test execution was interrupted while the beta simulator runner remained stuck materializing a worker, so this is compile verification, not a passing runtime CloudKit test.
- SDK source of truth: the Xcode 27 CloudKit headers and Swift interface under `iPhoneOS27.0.sdk/System/Library/Frameworks/CloudKit.framework`.
- Brownfield source of truth: `apple/project.yml`, `apple/ChronicleApp/CloudKitSyncModel.swift`, `src/store/index.ts`, `src/lib/chronicleSync.ts`, `src/lib/chronicleVersioning.ts`, `src/types/index.ts`, and `docs/data-architecture.md`.

## Findings

### [CRITICAL] T1 — The checked-in Apple app cannot access the declared CloudKit container

**Affected commitments:** AD-2, AD-8; data-model implementation steps 1, 6, and 8.

There is no `.entitlements` file, no `CODE_SIGN_ENTITLEMENTS` setting, and no iCloud/CloudKit container configuration in `apple/project.yml`. The container identifier exists only as a Swift string in `CloudKitSyncModel.swift:3-7`. Consequently, `CKContainer(identifier:)` against `iCloud.com.binion.chronicle` is not an exercisable assumption in the current target, and neither development schema creation nor a real-device private-database test is possible from this checkout as configured.

**Required correction:** Promote container/entitlement provisioning from a deferred operational footnote (`ARCHITECTURE-SPINE.md:161`) into a pre-implementation gate. Bind the exact entitlements (`com.apple.developer.icloud-container-identifiers`, CloudKit services, and ubiquity container environment as generated by Xcode), add them to every shipping Apple target, and require one signed-device smoke test that creates/fetches `ChronicleData-v1` before schema or sync work is considered ready. Do not claim production deployment until the container is present in the correct Apple Developer team and CloudKit Dashboard.

### [HIGH] T2 — The promised durable local transaction and immutable history do not exist in the current app

**Affected commitments:** AD-1, AD-3, AD-4, AD-5, AD-8; data-model protocol steps 1-3 and 5-8.

The native code is only value structs and three contract tests; it contains no CloudKit import, codec, repository, outbox, inbox, `CKSyncEngine`, or persisted engine serialization. The active Zustand code mutates UI state first and then fires an HTTP persistence call whose rejection is only logged (`src/store/index.ts:586-610`, `640-668`). Deletes physically remove local objects. Formation completions are truncated to 60 locally (`src/store/index.ts:612-626`) and 120 during portable merge (`src/lib/chronicleSync.ts:74-88`). Existing portable merges overwrite scalar values using date/order heuristics (`src/lib/chronicleSync.ts:36-71`, `111-168`) rather than creating branch revisions. This directly contradicts “reports success only after ... commit atomically,” “deletion is a revision,” and “older data stays retrievable.”

The architecture correctly labels the repository as future seed, but AD-1 is marked `[ADOPTED]` and the handoff reads as a contract for current adapters. A developer could incorrectly layer CloudKit over the existing mutable paths and silently violate every retention guarantee.

**Required correction:** Add an explicit cutover invariant: no current Zustand/HTTP mutation path may become a CloudKit producer. First implement the native transactional repository and make the web adapter call it; then migrate existing state into initial revisions. Identify the old fire-and-forget and destructive-delete functions as legacy paths that must be removed or routed through the repository before sync ships. Preserve full completion history as revision/event data rather than copying the existing `.slice(...)` behavior.

### [HIGH] T3 — CKSyncEngine atomicity is optional in the handoff but false by default in the relevant initializer

**Affected commitments:** AD-3, AD-4; data-model protocol step 4.

The handoff says to save revision and head “in one atomic CloudKit modify batch when possible” (`CLOUDKIT-DATA-MODEL.md:104-113`). In the Xcode 27 SDK, `CKSyncEngine.RecordZoneChangeBatch(recordsToSave:recordIDsToDelete:atomicByZone:)` defaults `atomicByZone` to `false`. Custom private zones support atomic modifications, but only when the batch requests them. “Revision before head” is not an ordering guarantee inside an atomic batch and should not be relied on.

For this schema, atomicity is not merely an optimization: publishing a head without its referenced revision breaks the record graph, while publishing a revision without advancing the head is acceptable only as a deliberately retained branch/retry state.

**Required correction:** Require `atomicByZone: true` for every batch containing a new revision plus its item-head mutation, and ensure all records use the same `ChronicleData-v1` zone. On `serverRecordChanged`, keep the unsent local revision/outbox entry, fetch the server head, resolve ancestry, and submit a new explicit atomic batch. Replace “when possible” and ordering language with this enforceable rule. Tests must inspect the produced `RecordZoneChangeBatch.atomicByZone` value.

### [HIGH] T4 — Complete JSON snapshots have no CloudKit size/sharding contract

**Affected commitments:** AD-3, AD-7; `ChronicleRevision.payload`; synchronized `ownedBook`, `ownedBookStudy`, and `aiThread` kinds.

Every revision stores a complete canonical JSON state in a CloudKit `Bytes` field (`CLOUDKIT-DATA-MODEL.md:44-55`). The contract gives no maximum payload size, sharding rule, or fallback to assets. This is especially unsafe for full AI conversations, generated study plans, OCR-derived owned-book state, or ever-growing event collections. `CKAsset` is the appropriate transport for larger file-backed values; the SDK documentation recommends assets for values more than a few kilobytes. Repeating a large complete snapshot for every immutable revision also creates uncontrolled private-database quota growth.

**Required correction:** Bind a maximum encoded revision payload well below CloudKit's record limit; fail closed before enqueue. Store large immutable content in `ChronicleAsset` (or shard append-only children such as AI messages/review events into their own records), with the revision containing encrypted hashes and stable asset IDs. Define asset lifecycle, deduplication posture, and behavior when quota blocks only part of a logical change. Add boundary tests at the chosen maximum.

### [HIGH] T5 — The sync scope can leak local file paths and unapproved copyrighted assets

**Affected commitments:** AD-6, AD-7; `ownedBook` synchronization.

The handoff correctly says never to upload Mac paths or unapproved imported files (`CLOUDKIT-DATA-MODEL.md:57-72`), but `ChronicleCloudSyncScope.syncedKinds` blindly includes every enum case (`CloudKitSyncModel.swift:101-113`) and the proposed codec source is the existing Zustand `OwnedBook`. That type contains `sourcePath`, `textPath`, `ChronicleSourceAssetRef.originalPath`, and managed `relativePath` (`src/types/index.ts:439-472`). The existing portable sync already copies complete `OwnedBook` values and asset maps (`src/lib/chronicleSync.ts:129-168`). A generic JSON codec would therefore upload exactly the paths the contract forbids, potentially alongside copyrighted/generated content.

**Required correction:** Define dedicated cloud DTOs per kind rather than serializing Zustand models. For `ownedBook`, whitelist user-authored metadata and approved asset identifiers; explicitly omit `sourcePath`, `textPath`, `originalPath`, `relativePath`, processing status, and local cache descriptors. Require an asset-rights state (`notEligible`, `userOwnedApproved`, etc.) before a `CKAsset` outbox entry can be created. Replace the category-string test with field-level codec tests using fixtures containing real absolute paths and secrets.

### [HIGH] T6 — “Mac, iPhone, and iPad” and “Handoff” exceed the shipping target reality

**Affected commitments:** AD-4, AD-10; data-model opening claim and implementation step 8.

The only native application target is iOS with `TARGETED_DEVICE_FAMILY = 2` (iPad only) and `SUPPORTS_MACCATALYST = NO` (`apple/project.yml:13-30`). There is no iPhone target, Mac target, or Mac Catalyst support. `ChronicleContinuation` is a CloudKit record and local expiry predicate only; no `NSUserActivity`, Handoff entitlement, activity type, universal-link/deep-link contract, or push/foreground trigger exists. Cloud replication plus polling can support cross-device continuation, but it is not Apple Handoff and cannot promise timely appearance on a target device by itself.

**Required correction:** Either rename the capability everywhere to “cloud continuation after sync” and describe discovery/refresh timing, or explicitly add Apple Handoff as a separate transport using `NSUserActivity` while keeping the CloudKit item/revision pointer as durable state. Make iPhone/Mac target creation a prerequisite for claims and two-device tests involving those platforms. Until then, scope the verified implementation to iPad.

### [MEDIUM] T7 — CKSyncEngine availability is misstated

**Affected commitment:** Stack row in `ARCHITECTURE-SPINE.md:116-125`.

Xcode 27's Swift interface marks `CKSyncEngine` itself available on iOS 17.0/macOS 14.0. Only particular context-bearing event properties, such as `WillFetchChanges.context` and `DidFetchChanges.context`, are iOS 17.2+. The row “CKSyncEngine | iOS 17.2+ API” is therefore inaccurate. Because Chronicle currently deploys to iOS 27, this does not block the build, but it is a false technology fact.

**Required correction:** State `CKSyncEngine: iOS 17.0+; selected event context APIs iOS 17.2+; compiled with iOS 27 SDK`. Also distinguish the Xcode 27 compiler (Swift 6.4) from the project's selected Swift 6 language mode if the stack intends to identify actual toolchain versions.

### [MEDIUM] T8 — Engine state and the application outbox are conflated

**Affected commitments:** AD-8; data-model protocol step 8.

`CKSyncEngine.Configuration` accepts a prior `State.Serialization`, and the engine emits updated serialization through state-update events. Its pending changes identify record IDs; the delegate must still provide the corresponding `CKRecord` values. The handoff says to retain “CKSyncEngine state and pending outbox changes” but does not bind when each is persisted or how they recover together. Persisting only the engine serialization loses record bodies; persisting only the app outbox loses server change-token state and may refetch/retry unpredictably.

**Required correction:** Define two distinct durable artifacts: (1) opaque engine state serialization, saved on every state-update event, and (2) application outbox rows containing enough immutable domain data to recreate each record. On launch, restore serialization first, reconcile engine pending IDs with outbox rows, add missing pending changes idempotently, and quarantine orphaned IDs. The app database transaction cannot atomically include a later CKSyncEngine state-update callback, so specify reconciliation rather than implying one cross-system transaction.

### [MEDIUM] T9 — Encryption claims need provisioning and threat-model precision

**Affected commitment:** AD-7.

The API claims are real: iOS 27 provides `record.encryptedValues`, references cannot be encrypted, encrypted fields cannot be indexed or queried, and `CKAsset` is encrypted by default. The proposed tables correctly leave encrypted fields unindexed. Two caveats are missing:

1. CloudKit permits encryption only for new schema fields; an existing plain field cannot later be converted to encrypted. The development schema must therefore be seeded using `encryptedValues` from the first record save, before production promotion.
2. Apple's header says encryption keys are exclusive to the owner/share participants when Advanced Data Protection is enabled. “Encrypted by CloudKit” must not be presented as unconditional end-to-end encryption against Apple for users without ADP.

**Required correction:** Add a schema-provisioning test that creates every protected field through `encryptedValues` in a clean development environment, and document the protection as CloudKit encrypted fields/assets with ADP-dependent end-to-end properties. Keep references and the minimal query metadata plain by design.

### [MEDIUM] T10 — Index declarations are valid but overbroad and unconnected to actual access paths

**Affected artifact:** all `Index` columns in `CLOUDKIT-DATA-MODEL.md`.

CloudKit supports queryable and sortable indexes configured in the schema, and it rejects indexes on encrypted fields. That part is technically sound. However, CKSyncEngine's custom-zone change feed and direct fetch by `CKRecord.ID` do not require these application indexes. The handoff marks many fields queryable/sortable without naming a query that consumes them, including `currentRevision`, schema versions, tombstone flags, and multiple references. Every production index becomes schema and operational surface.

**Required correction:** Supply an access-path table (`fetch by record ID`, `zone changes`, `history by item + createdAt`, `continuations by expiresAt`) and keep only indexes needed by real `CKQuery` predicates/sorts. For history, verify whether the intended compound predicate/sort is supported in the deployed schema; otherwise fetch ancestry by known IDs or introduce a deliberate lookup field. Index creation must occur in development and be promoted before clients depend on it.

### [MEDIUM] T11 — Continuation expiry and archive guarantees are semantic, not CloudKit retention features

**Affected commitments:** AD-2, AD-10; `ChronicleContinuation` and reinstall behavior.

CloudKit does not automatically TTL-delete a record because it has `expiresAt`; `ChronicleContinuation.isExpired` only prevents local use. Likewise, the private database is a synchronization store controlled by the user's iCloud account, quota, app/container state, and explicit deletions—not an independent backup/archive service with an absolute retention SLA. The app can make historical revisions retrievable by never deleting them, but “CloudKit retains” and “app reinstall restores” require the same iCloud account, intact zone, deployed schema, successful sync, and sufficient quota.

**Required correction:** Say continuations “expire logically after seven days” and decide whether expired records are intentionally retained or separately garbage-collected. Rephrase “archive” as “durable private replica retaining immutable revisions until explicit purge/account/container loss,” and document reinstall preconditions. Product backup/export is a separate concern.

### [LOW] T12 — The model structs do not prove the CloudKit schema contract

`CloudKitSyncModel.swift` imports only Foundation and models UUIDs/`Data`; `ChronicleCloudAsset` has no file URL or blob representation, and no function constructs `CKRecord.ID` with the required zone, sets references, writes encrypted values, or validates record types. Its three tests verify tombstone payload clearing, parent deduplication, and category strings, not CloudKit compatibility.

**Required correction:** Add an actual CloudKit codec layer and pure unit tests that inspect produced `CKRecord` objects: record type/name/zone, reference actions, plain versus encrypted key sets, tombstone shape, asset field placement, and decode round trips. Then add signed development-container integration tests separately.

## Verified commitments that may remain

- A custom record zone in the user's private database is the correct CloudKit primitive. Custom private zones support zone change tracking, same-zone references, and atomic record modifications. Explicitly create and save the zone before saving records into it.
- Change-tag protection via `.ifServerRecordUnchanged` produces `CKError.serverRecordChanged` and is appropriate for the mutable `ChronicleItem` head.
- Same-zone `CKRecord.Reference` fields are valid for item/revision/asset relationships. Use reference action `.none`; `.deleteSelf` would conflict with revision retention and future explicit purge rules.
- `CKRecord.encryptedValues` is available and appropriate for the named private scalar/data fields. Encrypted fields cannot be indexed or queried. References remain plain for server-side use.
- `CKAsset` is encrypted by default and is appropriate for approved user-owned files. The app must move downloaded staging files into its own container promptly; CloudKit's staging URL is temporary.
- Development and production CloudKit schemas are separate. Unknown production record types/fields fail, so production promotion must follow schema/codec integration testing.
- One `CKSyncEngine` coordinator per process, restored from opaque state serialization and backed by a durable application outbox, is a coherent ownership boundary.

## Required disposition before handoff

1. **Autofix the spine/data model:** correct CKSyncEngine availability; require `atomicByZone: true`; remove batch-order wording; qualify encryption, continuation expiry, archive/reinstall, and platform claims.
2. **Discuss and bind:** record payload ceiling/sharding; outbox/engine-state reconciliation; minimal query/index access paths; cloud DTO allowlists and asset-rights gate.
3. **Implementation gate:** add entitlements/container, transactional repository, codecs, and CKSyncEngine coordinator before claiming that the current app satisfies AD-1 through AD-10.
4. **Verification gate:** pass codec unit tests, process-restart/outbox recovery tests, two signed-device offline-conflict tests, quota/asset failure tests, and development-to-production schema rehearsal.
