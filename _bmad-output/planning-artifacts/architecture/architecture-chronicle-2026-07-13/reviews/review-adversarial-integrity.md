# Adversarial Integrity Review — Chronicle CloudKit Sync and Handoff

## Verdict

The documents establish a sound local-first intent, but they are not yet a sufficient wire-and-replication contract for independently built Mac, iPhone, and iPad clients. Each client could honestly claim compliance with AD-1 through AD-10 while making different choices at unspecified protocol seams. Those choices can produce incompatible hashes and payloads, undiscoverable conflict branches, tombstone resurrection, incomplete history, cross-account disclosure, and handoff navigation before required content is durable locally.

The central structural defect is that `ChronicleItem.currentRevision` is the only cloud-visible head while AD-4 permits unresolved branches. An immutable revision can preserve bytes in CloudKit without preserving a reachable, synchronized branch. The documents need an explicit convergence protocol, not only a promise to preserve both histories.

## Independent-client counterexamples and findings

- A Mac canonicalizes JSON by recursively sorting keys and emitting NFC Unicode, while an iPhone uses `JSONEncoder.sortedKeys` without Unicode normalization and an iPad preserves source key order. All three produce UTF-8 canonical JSON and SHA-256 as required, yet the same logical payload has different bytes and hashes. Specify a normative canonicalization algorithm, including Unicode normalization, number representation, escaping, null handling, date formatting, set ordering, and test vectors that every target must pass.

- The synchronized-kind table names payload sources and merge postures but defines no versioned wire schemas. A Mac can encode a date as a numeric epoch, an iPhone as an ISO string, and an iPad as a day-only value while all label the payload `contentSchemaVersion = 1`. Define required and optional fields, field types, enum values, stable nested identifiers, omission/default rules, unknown-field preservation, and migrations for every synchronized kind. The current source type names are not a cross-platform data contract.

- Two devices can both upload divergent immutable revisions, then race to update the single `ChronicleItem.currentRevision`. One update wins and the loser receives `serverRecordChanged`. If the losing device creates only a local “visible user-resolution task,” as the protocol permits, its branch has no cloud head record and no required device-independent way to discover it. A newly installed iPad sees only the winner unless it performs an unspecified full query of every revision for the item. Define a durable cloud branch-head/conflict record or a head-set representation, and do not declare conflict preservation complete until every live branch is cloud-discoverable.

- “Create a merge revision or a visible user-resolution task” permits incompatible outcomes for the same conflict. The Mac may create an automatic merge, the iPhone may leave a local task, and the iPad may create a different merge; all obey AD-4. Define which conflicts are automatically mergeable, the deterministic merge function and parent ordering, how unresolved conflicts are represented and synchronized, and how competing merge revisions converge.

- A Mac can treat a concurrent tombstone as deletion-wins, an iPhone can merge the edited payload over the tombstone, and an iPad can expose both branches while selecting the edit as head. Every implementation preserves both revisions, but two resurrect the item in different ways. Define tombstone conflict semantics explicitly: whether deletion is a barrier, what head is selected during unresolved delete/edit conflict, how the UI represents the nonselected edit, and the only operation allowed to restore visible content.

- `ChronicleItem.isDeleted`, `ChronicleItem.currentRevision`, and the referenced revision's `isTombstone` duplicate the same state without a stated authority rule. A partially implemented save, bad migration, or future client can produce `isDeleted = 0` with a tombstone head. Define the authoritative value, require validation of the invariant on send and receive, and specify quarantine/repair behavior. Prefer deriving deletion locally from the resolved head unless the denormalized field is demonstrably required.

- The protocol enqueues an item-head save for every local mutation, but does not define outbox compaction. If an offline Mac makes revisions R1, R2, and R3, one client may submit three head mutations using one stale server change tag, another may coalesce directly to R3, and another may upload only R3 and omit ancestors. Define that every referenced ancestor is durably uploaded before exposure of the final head, how repeated mutations of the same `CKRecord.ID` are coalesced, when the server change tag is refreshed, and how pending operations are acknowledged idempotently.

- “Save the revision before its item head in one atomic CloudKit modify batch when possible” is not a safety rule. One implementation may use an atomic operation, another may issue ordered non-atomic saves, and another may retry the failed head without rechecking revision availability. Require a precise dependency state machine: a head must never be sent until its revision, parents, and required assets are confirmed saved; orphan revisions are acceptable, dangling heads are not; partial successes must be reconciled before retry.

- New-item creation has an underspecified dependency cycle: the revision references its owning `ChronicleItem`, while the item head references the revision. Different clients may save either side first or rely on one atomic batch, and inbound validation may reject whichever record arrives first as having a missing reference. State whether dangling CloudKit references are allowed during creation, require atomic creation if that is the solution, and define staging of valid-but-incomplete dependency graphs rather than quarantining them as corrupt.

- Incoming zone changes can deliver a head before its revision or an asset after its revision. AD-9 says to authenticate references and atomically commit an inbox batch, but does not distinguish “dependency not fetched yet” from “invalid reference.” A strict Mac may quarantine the head, while a permissive phone exposes incomplete content. Define unresolved dependency staging, retry/fetch behavior, completeness predicates, and the exact point at which an item becomes readable or its head advances locally.

- A continuation cannot prove content completeness. It points to a revision, but neither the revision nor the continuation declares the complete set of required asset IDs and hashes. A target can fetch the revision, find zero currently returned assets, treat that as complete, ask the user to continue, and navigate before a delayed asset change arrives. Put a manifest of required assets in the immutable revision payload or a referenced immutable manifest, then require all listed bytes to be hash-verified and atomically committed before acceptance and navigation.

- Handoff's control protocol is only prose. It does not define continuation lifecycle states, target claiming, duplicate acceptance on two devices, timeout behavior, exact-revision versus latest-head presentation, or what happens when the pinned revision is quarantined, schema-incompatible, tombstoned, or missing. Define a target state machine such as discovered, resolving, locally-complete, accepted, opened, expired/failed; navigation must be gated solely on locally-complete plus explicit acceptance, never on receipt of the continuation record itself.

- `ChronicleContinuation.item` is described as optional for built-in routes, but its CloudKit field type and absence rules are not specified; `revision` is simultaneously described as pinning exact state even though a built-in route may have no record state. Define required-field combinations as a tagged continuation target (`record` versus `builtInRoute`) and reject all other combinations so clients do not invent incompatible null/reference behavior.

- “Devices may evict old revision payloads locally, but must retain enough ancestry metadata” has no computable minimum. One client may retain parent IDs only for recent revisions, another may retain a Bloom-like summary, and another may depend on CloudKit queries; they can reach different fast-forward decisions after long offline periods. Require retention of the complete reachable parent graph or define an exact on-demand ancestry proof protocol. Unknown ancestry must never be treated as non-ancestry or as permission to select a head.

- History retrieval is not specified beyond fetching missing revisions on demand. CloudKit query ordering by `createdAt` is unsafe under clock skew, parent reference lists are not ordered, pagination and completeness are undefined, and an orphaned conflict branch may not be reachable from the selected head. Define history as graph traversal by revision IDs and parent edges, define stable pagination/cursors and completeness, include all live branch roots, and use timestamps only for display—not ancestry or conflict resolution.

- Cloud account transitions are absent from the contract. A device signed out of account A may continue accumulating local writes, then sign into account B; a compliant coordinator could upload account A's local records into B's private database because “continue locally” and later retry are both required. Bind every local replica, outbox entry, token, and zone state to a stable CloudKit account identity/replica epoch; freeze and explicitly re-home or retain account-A data on account change, and never automatically send it to account B.

- Zone deletion, subscription reset, token expiration, restore-from-backup, and CKSyncEngine state loss have no recovery algorithm. Implementations can interpret an empty zone as authoritative deletion, repopulate it from local data, or silently create a second logical replica. Specify reset semantics, full-refetch behavior, token commit ordering, zone recreation authority, and how an app reinstall distinguishes an empty new account from a deleted or temporarily unavailable zone.

- The local transaction required by AD-1 names item, revision, and outbox but not asset ingestion. A revision can commit successfully while its referenced file still exists only at a transient file URL; later the outbox cannot upload it, yet the UI already reported a durable write. Require user assets and their immutable metadata to be copied into app-owned durable storage in the same logical commit before a revision that references them can become the local head.

- `ChronicleAsset` says an asset is attached to the revision that introduced it, while later revisions contain a “complete” state, but no field formally lists assets used by that complete state. One client may query all assets ever introduced by ancestors, another may list asset IDs inside payload JSON, and another may duplicate assets per revision. Define immutable asset identity, revision-to-asset membership, reuse across revisions, removal semantics, and garbage-retention rules. “Address by hash” conflicts with UUID record names unless the mapping and collision policy are specified.

- UUID and record-name conventions do not completely define identity encoding. Clients may accept uppercase UUID input, brace-wrapped UUIDs, non-v4 UUIDs, or lowercase only; two textual forms can map to the same conceptual ID but different CloudKit record names. Specify accepted UUID format/version, byte-to-string serialization, lowercase normalization at creation and decode, namespace uniqueness, and rejection rules. Also define the response to an immutable revision record-name collision with different bytes; silently changing the UUID can break queued references.

- Immutable CloudKit records are protected only by convention. The data model says revisions and assets are never updated after successful save, but does not require compare-before-accept behavior on `serverRecordChanged`. A buggy or newer client can attempt to overwrite an existing immutable record, and another client may accept server bytes under a locally known ID without verifying identity. Require create-only saves for immutable types, content comparison on collision, permanent quarantine of same-ID/different-content records, and no automatic overwrite or re-ID of a published graph node.

- `updatedAt` and revision `createdAt` come from device clocks but their semantic use is not constrained. A clock-skewed iPad can sort a new revision years before its parent, and clients may use timestamps to choose a winner even though AD-4 does not forbid that implementation detail. State that device timestamps are informational only; ancestry and explicit deterministic merge rules govern convergence. If trustworthy chronology matters, add a server-observed timestamp that is not used to rewrite immutable payload identity.

- Schema compatibility is one-sided. A v1 device quarantines a future head but can continue creating v1 edits from an older local head; when uploaded, that edit branches behind the v2 head. The documents do not say whether the old client may publish, whether its branch must remain visible, or how a newer client recovers it. Define per-kind read/write compatibility ranges, preserve unknown fields when required, block only unsafe mutations with an explicit local state, and require future-head branch discovery rather than allowing an old client to make a quarantined lineage disappear.

- CloudKit field-size and record-limit behavior is omitted. A “complete canonical JSON state” may exceed the permitted encrypted Bytes size, parent lists can grow through pathological merges, and a modify batch can exceed operation limits. Different clients may fail, truncate, or invent incompatible chunking. Set contract-level payload and graph limits and define one chunk/manifest format, or require oversized content to use assets before local commit is reported as syncable.

- References do not specify CloudKit reference delete actions. Although automatic purge is deferred, a future operational or buggy record deletion can cascade differently depending on client-created reference metadata and destroy revisions or assets that the architecture promises to archive. Require `.none` for archival graph references and make physical record deletion impossible through the ordinary sync codec.

- The migration step says to preserve current IDs “inside payload metadata,” but does not define the stable `ChronicleItem` UUID derivation, migration marker, or multi-device deduplication. Mac and iPhone can independently migrate equivalent pre-cloud local objects into different item UUIDs and then synchronize duplicates forever. Define whether legacy IDs become item IDs through a deterministic namespace mapping, how the one-time migration is recorded per dataset, and how independently migrated duplicates are detected without merging unrelated records.

## Required exit criteria before implementation handoff

- Publish normative payload schemas and canonicalization/hash test vectors for every synchronized kind.
- Add a cloud-durable representation of all live branch heads and unresolved conflicts, including delete/edit conflicts.
- Specify send, receive, outbox-coalescing, dependency-staging, reset, and account-transition state machines.
- Define exact ancestry retention/traversal and history completeness rules.
- Add immutable asset manifests and a handoff completeness gate that cannot open navigation early.
- Supply cross-platform conformance scenarios covering offline multi-edit, concurrent delete/edit, competing merges, delayed dependencies, future schema, account switch, zone reset, reinstall, and continuation with missing assets.

Until those are contractual and tested, the architecture is suitable as a design direction but unsafe as an independent-team implementation handoff.
